# ADR-0072 Removed Limitations Report — Clone URL Encoding & @-Passthrough Edge Case

> **Platform scope:** Both issues concern **GitLab only**. GitHub does not use `oauth2:` token embedding or `@`-based credential detection in the same way.

---

## Overview

The PR for GitLab feedback polling removed the entire "Known Limitations and Future Work" section from `docs/adr/0072-platform-abstraction-layer.md` (commit `88ff290`). Two of the six entries in that section described code that was **not touched** by the PR and still has the documented limitations:

1. **GitLab Clone URL URL Encoding** — `clone_url()` in `gitlab.rs`
2. **Agent Runner @-Passthrough Edge Case** — `authenticated_clone_url()` in `client.rs`

Removing them from the ADR means a future reader trusts the ADR and may ship a token with a special character or an `@`-containing subgroup path into a limitation the doc now claims is gone.

---

## Issue 1: GitLab Clone URL URL Encoding

### Affected file
`services/control-plane/src/integrations/gitlab.rs` — `clone_url()` (line 543-559)

### Current code

```rust
fn clone_url(&self, repo: &RepoRef) -> String {
    let base = self.api_url.strip_suffix("/api/v4").unwrap_or(&self.api_url);
    let host = base.split_once("://").map(|(_, h)| h).unwrap_or(base);
    format!("https://oauth2:{}@{}/{}.git", self.token, host, repo.full_name)
}
```

### The limitation

The `token` and `repo.full_name` are interpolated directly into the URL without URL-encoding. The URL format is:

```
https://oauth2:{token}@{host}/{full_name}.git
```

GitLab PATs are alphanumeric + hyphens (`glpat-xxxxxxxxxxxxxxxxxxxx`), and project paths are typically alphanumeric + hyphens + underscores + slashes. In the normal case this produces valid URLs.

However, if a token or project path contains characters that have special meaning in URLs (e.g., `@`, `:`, `/`, `#`, `?`, `%`), the resulting URL would be malformed:

- A token containing `@` would break the `oauth2:TOKEN@host` format — the `@` would be interpreted as the credential separator prematurely.
- A project path containing `#` would truncate the URL at the fragment.
- A project path containing `?` would be interpreted as a query string.

### Risk assessment

**Low in practice.** GitLab PATs are generated by GitLab and are always `glpat-` prefixed alphanumeric strings. Project paths follow GitLab's naming rules which restrict special characters. However, the limitation is real and should be documented so operators are aware.

### Why it wasn't fixed in this PR

The comment in the code (line 547-549) explicitly states: *"URL-encoding would break the OAuth2 format (`:` in token would be misinterpreted as scheme separator)."* The `oauth2:TOKEN@host` format relies on the `:` being a literal separator between the username (`oauth2`) and the password (token). URL-encoding the `:` to `%3A` would break git's credential parsing. A proper fix would require a different URL construction approach (e.g., using git's credential helper or a `.netrc` file), which is out of scope for this PR.

### Recommendation

Restore the ADR-0072 entry to document this as a known, low-risk limitation.

## Issue 2: Agent Runner @-Passthrough Edge Case

### Affected file
`services/agent-runner/src/bootstrap/client.rs` — `authenticated_clone_url()` (line 127-135)

### Current code

```rust
pub fn authenticated_clone_url(&self) -> String {
    match self.clone_url.strip_prefix("https://") {
        // Already authenticated by the control plane — use as-is.
        Some(rest) if rest.contains('@') => self.clone_url.clone(),
        // Splice the token in (GitHub's x-access-token:<token>@ form).
        Some(rest) => format!("https://x-access-token:{}@{rest}", self.token),
        None => self.clone_url.clone(),
    }
}
```

### The limitation

The function uses `rest.contains('@')` to detect whether a URL already has credentials embedded. This works correctly for:

- **GitHub**: `https://github.com/owner/repo.git` — no `@`, so token is spliced in → `https://x-access-token:TOKEN@github.com/owner/repo.git`
- **GitLab**: `https://oauth2:TOKEN@gitlab.com/group/repo.git` — has `@`, so passed through unchanged

The edge case: if a URL path contains `@` (e.g., `https://github.com/owner@team/repo.git`), the function would incorrectly detect it as "already authenticated" and pass it through without splicing the token. The clone would then fail with an authentication error.

### When could this happen?

- **GitHub**: GitHub usernames/orgs cannot contain `@`, so this is not a real-world issue for GitHub.
- **GitLab**: GitLab subgroup names cannot contain `@` either (GitLab restricts to alphanumeric + hyphens + underscores), so this is also not a real-world issue for GitLab.
- **Future platforms**: If a future platform allows `@` in path segments, this would be a problem. But the trait is designed so each platform provides its own `clone_url()`, so the control plane controls the URL format.

### Risk assessment

**Extremely rare.** Neither GitHub nor GitLab allow `@` in usernames, org names, or subgroup paths. The guard is correct for all currently supported platforms. The edge case is documented for future review if a platform with different naming rules is added.

### Why it wasn't fixed in this PR

The PR body lists `client.rs` as out of scope. The agent-runner is platform-agnostic by design (ADR-0017), and the `@` detection is a pragmatic heuristic that works for all current platforms. A proper fix would require parsing the URL to distinguish `@` in the authority section from `@` in the path, which adds complexity for a case that doesn't occur in practice.

### Recommendation

Restore the ADR-0072 entry to document this as a known, rare edge case.
